You control how much your tenants can brand themselves.

A read on the white-label branding npm package plan — shadcn + Tailwind adapters, tiered control the developer sets per tenant — checked against current white-label SaaS buying behavior.

Verdict: the plan is sound and well-timed. The market data supports the two ideas that matter most — tiered control as a real buying criterion, and framework-agnostic tokens with thin adapters as the right technical shape. One gap surfaced: the plan doesn't yet define how per-tenant theming stays isolated as tenant count scales past a few hundred.
  • Depth of rebranding control is an explicit evaluation criterion for buyers — some platforms allow only a logo swap, others support full domain masking and custom dashboards. source: cameldigital.co, 2026 white-label SaaS guide
  • Applying per-tenant branding without layout shift is named as one of three core technical problems in production white-label systems, alongside domain routing and outbound email. source: viprasol.com, 2026
  • Enterprise buyers test for branding completeness everywhere — custom domain, no vendor logo in UI, error pages, emails, mobile views. source: toucantoco.com, 2026
  • At scale, per-tenant theming has to be enforced through configuration, not one-off engineering per customer — this is the architectural gap to close before scaling tenants. source: omni.co, 2026

02

03
Direct
Per-role color pickers, still APCA-validated.
04
Raw
Full token access. No guardrails — expert / agency tier.

Before writing the adapters

  • Tenant isolation strategy — scoped CSS custom properties per tenant, or per-tenant stylesheet injection. Changes adapter output shape, decide first.
  • Runtime vs. build-time generation — Forge's multi-tenant snapshot model suggests runtime CSS variables as the default.
  • Validation boundary — APCA contrast enforced through Direct tier; Raw tier is explicitly unguarded.
